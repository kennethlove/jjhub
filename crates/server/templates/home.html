Git forges model branches. Jujutsu models changes.

jjhub hosts the model you actually work in. The merge request follows the change, not the ref.

Change-anchored merge requests

A merge request is a repository plus a change-id, for example acme/web-ui@kqvryyuz. It survives every history edit you make locally: rebase, squash, or amend, and the review stays attached.

Edit-in-place review

Every push is a new Revision of the same change. Old revisions and their comments stay readable, so reviewers see what changed and why, not just the latest snapshot.

Stacks from the graph

Stack parentage comes from commit parents, not from a manually maintained branch chain. Merge the bottom merge request and jjhub squashes it, then server-rebases the rest of the stack.

Git compatibility

Plain git clone works. jjhub serves standard Git protocols, so CI, tooling, and collaborators on Git keep working while jj users get the full model.

Merge the bottom. The stack follows.

Three changes stacked on acme/web-ui. Merge the parent and jjhub rebases its children onto the new trunk, keeping every change-id intact.

Stacked merge requests inherit their shape from the commit graph. There is no branch chain to maintain and nothing to re-request after a rebase: each review stays anchored to its change-id while the commits under it move.

Self-hosting takes one file and two secrets.

jjhub ships as a container. Bring a host, a domain, and a Postgres volume.

1

Start the stack

Grab the compose file from the repository and bring it up. jjhub serves Git over SSH and HTTP, with a Postgres database beside it.

curl -O https://raw.githubusercontent.com/kennethlove/jjhub/main/docker-compose.yml
docker compose up -d
2

Set the secrets

Put the database password and the session signing key in an environment file next to the compose file. Nothing else is required for a first run.

# .env
POSTGRES_PASSWORD=change-me-per-host
SESSION_SECRET=32-bytes-or-more-of-random

Full instructions, backup notes, and reverse-proxy examples live in the README.

Early development

Honest about where this is.

jjhub is pre-1.0 and runs on a single node. The core loop works: host repositories, push changes, review revisions, merge stacks. Expect breaking changes in the storage format while the MVP settles.

Conflict-tolerant hostingAccept and store commits with conflicts; surface them in the review instead of rejecting the push.
Operation-log auditA queryable log of every server-side operation, straight from jj's operation model.
Server-side immutability policyConfigure which heads the server refuses to rewrite, enforced before any merge runs.
Revset searchQuery changes with real revsets instead of a keyword box bolted onto a filter.
